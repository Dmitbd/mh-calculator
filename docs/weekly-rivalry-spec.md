# Weekly Rivalry Calculator Spec

Этот документ фиксирует продуктовую и техническую логику самостоятельной функции еженедельного соперничества для трёх событий: `Вавилонская башня`, `Карта зодиака` и `Звериные эхо`.

## Scope

Каждый экран реализует один и тот же пользовательский сценарий:

- ввод основного ресурса события и персональных сундуков еженедельного события;
- расчёт шкалы соперничества до `12 000` очков;
- два источника кешбэка соперничества: основной ресурс из обычных узлов и полученные со шкалы сундуки;
- пять разделов заданий по шесть последовательных заданий;
- награды каждой строки и отдельная награда за завершение раздела;
- собственный кешбэк основного ресурса из выполненных заданий;
- раздельные сводки всех наград соперничества и заданий;
- опциональную взаимную связь включённых источников между зонами;
- независимое локальное сохранение каждого события, сброс и встроенную инструкцию.

Калькулятор не синхронизируется с сервером игры. Пороги, награды, названия и иконки являются локальным snapshot клиента версии `1.48.0`.

## Input Model

Состояние каждого события имеет один общий тип:

```ts
type WeeklyRivalryInput = {
  ownedSpendResource: number;
  ownedWeeklyEventChests: number;
  includeRivalryCashback: boolean;
  includeWeeklyEventChestCashback: boolean;
  includeQuestCashback: boolean;
  includeSharedCashback: boolean;
};
```

Основной ресурс и собственные сундуки являются общими исходными значениями для обеих зон. Каждый собственный сундук сразу считается одним основным ресурсом выбранного события. Количества нормализуются в целые числа от `0` до `1 000 000 000`; нечисловые и бесконечные значения превращаются в `0`, дроби округляются вниз.

Все четыре галочки по умолчанию и после сброса выключены:

- `Учитывать кешбэк соперничества` — повторно использует основной ресурс из наград обычных узлов шкалы;
- `Учитывать кешбэк «Персон. сундук еженед. события»` — повторно использует полученные со шкалы сундуки по правилу `1 сундук = 1 основной ресурс`;
- `Учитывать кешбэк заданий` — повторно использует основной ресурс из уже выполненных заданий;
- `Учитывать общий кешбэк` — передаёт результат каждого включённого источника также во вторую зону.

Выключенная галочка не скрывает достигнутые награды и не меняет поля ввода; она отключает только повторное использование своего источника.

## Calculation Modes

При выключенном общем кешбэке зоны изолированы:

```text
Основной ресурс + собственные сундуки ──► соперничество
                                      └─► задания события

Награды соперничества ──► только соперничество
Награды заданий       ──► только задания события
```

Кешбэк заданий не меняет соперничество. Основной ресурс и полученные сундуки шкалы не меняют задания. Полученные сундуки продолжают каскад соперничества только при включённой галочке сундука.

При включённом общем кешбэке каждый активный источник добавляется одновременно в обе зоны:

- основной ресурс из узлов — только если включён кешбэк соперничества;
- сундуки из крупных узлов — только если включён кешбэк сундука;
- основной ресурс из выполненных заданий — только если включён кешбэк заданий.

Одна общая галочка без включённых источников не меняет результат. После каждого добавления модель повторно проверяет узлы и задания. Каждый ID узла и задания применяется один раз, поэтому каскад конечен. Награды завершённого раздела входят в сводку заданий, но не являются источником дальнейшего каскада. Сводки двух зон никогда не объединяются.

## Rivalry Score And Reward Track

- один основной ресурс или один собственный сундук дают `30` очков;
- шкала содержит `16` узлов с шагом `750` и максимумом `12 000`;
- узлы `3000`, `6000`, `9000`, `12 000` помечены как крупные;
- обычный узел возвращает по `2` каждого из трёх основных ресурсов;
- крупный узел возвращает `10` персональных сундуков (`600053`).

Базовые очки равны `(ownedSpendResource + ownedWeeklyEventChests) × 30`. Итоговые очки могут превышать `12 000`, но число открытых узлов ограничено конфигурацией. Узлы обрабатываются по возрастанию порога, а сводка соперничества показывает иконку, название и количество каждого возможного ресурса, включая нули.

Шкала визуально повторяет паттерн `Антиквариата`: четыре строки по четыре сундука, соединяющая линия, золотой достигнутый прогресс, увеличенный специальный сундук и зелёная галочка на открытом узле. Представление использует `isSpecial` из конфигурации, а не позиционное правило. Награды узла показываются в сводке, а не внутри сундука.

## Event Quests

Все три события содержат пять разделов по шесть заданий. Пороги одинаковы:

| Раздел | Пороги заданий |
| --- | --- |
| 1 | `5`, `10`, `20`, `30`, `50`, `80` |
| 2 | `90`, `110`, `130`, `160`, `190`, `240` |
| 3 | `270`, `310`, `350`, `400`, `450`, `520` |
| 4 | `570`, `630`, `690`, `760`, `830`, `920` |
| 5 | `990`, `1070`, `1150`, `1240`, `1330`, `1440` |

Один основной ресурс или собственный сундук дают одно очко задания. Каждая строка показывает четыре игровые награды и прогресс `текущее / порог`. Выполненная строка получает приглушённый зелёный стиль и галочку. После выполнения всех шести строк так же отмечается отдельная награда раздела.

Кешбэк заданий продвигает расчёт только наградой, чей `resourceId` равен основному ресурсу текущего события. Остальные награды остаются видимыми, но не меняют прогресс. Точные наборы наград для 30 заданий и пяти разделов являются event-specific и хранятся в трёх валидируемых JSON-конфигурациях.

## UI Contract

Порядок блоков на каждом экране:

1. шапка с названием события;
2. кнопка `? Инструкция`;
3. заголовок `Калькулятор событий <название события>`;
4. карточка `Мои ресурсы` с полями основного ресурса и сундуков;
5. отдельная галочка `Учитывать общий кешбэк`;
6. зона `Соперничество`: две собственные галочки, очки, шкала и сводка;
7. зона `Задания события`: собственная галочка, пять разделов и сводка;
8. кнопка `Сбросить расчёт`.

Под ресурсами указано, что основной ресурс и сундуки используются в соперничестве и заданиях. Подпись обычного кешбэка и кешбэка заданий имеет вид `<Основной ресурс> из наград`; подпись сундука — `1 сундук = 1 <основной ресурс>`. Галочки источников остаются в своих зонах, а общий переключатель визуально отделён под исходными ресурсами.

Обе сводки повторяют карточный паттерн `Антиквариата`: игровая иконка, название и крупное числовое количество. Нулевые карточки не скрываются. Сводка содержит только реальные награды достигнутых узлов или заданий и не дублирует пересчёт сундуков, исходные ресурсы или итоговый прогресс служебными строками.

## Instructions

Каждый маршрут `/manual` использует общий экран инструкции и соответствующую конфигурацию. Инструкция объясняет:

- участие обоих исходных ресурсов в двух зонах;
- правило `30` очков соперничества и `1` очко задания;
- назначение четырёх выключенных по умолчанию галочек;
- изолированный режим и взаимный каскад;
- однократный учёт награды;
- отдельные сводки и поведение сброса.

Текст одинаков по структуре для трёх событий; название и грамматические формы основного ресурса берутся из конфигурации.

## Persistence

Каждое событие использует отдельный ключ `weekly-rivalry:<event-id>:v1`. Запись содержит `schemaVersion: 1`, нормализованные два количества, четыре галочки и время обновления. Вычисленный результат не хранится. Запись другой версии схемы, повреждённые данные или недоступный storage возвращают начальное состояние. Записи одного экрана выполняются последовательно; сброс не затрагивает другие события и калькуляторы.

## Game Data And Assets

Runtime source of truth:

- `tower-of-babel.json`;
- `zodiac-map.json`;
- `beastly-echoes.json`;
- общий словарь `resources.json`.

Snapshot подготовлен из клиентских таблиц версии `1.48.0`: `OlympusScoreTable`, `OlympusTaskRewardTable`, `WeeklyTaskTable` и `CustomizeBoxResourceTable`. Имена иконок сверены со sprite manifest той же распаковки; все 30 нумерованных PNG ресурсов в `public/img/weekly-rivalry` совпадают с извлечёнными спрайтами, а отдельный `rivalry-chest.png` используется шкалой узлов. Единственная нормализация текста — удаление хвостового пробела у имени `Эхо-монеты`. Поле `sourceVersion` обязано быть ровно `1.48.0`; runtime-валидатор проверяет версию, а integrity-тест фиксирует SHA-256 всех четырёх подготовленных JSON.

Для соблюдения web-бюджета конфигурации хранят event-specific награды компактными парами `[resourceId, amount]`. Общие метаданные ресурсов находятся в `resources.json`, а единые трек соперничества, пороги заданий и структурные инварианты собираются один раз на catalog boundary. В UI всегда поступает полный валидированный `WeeklyRivalryEventConfig`.

Валидатор проверяет event ID, обязательные грамматические формы, безопасные положительные числа, уникальные ID узлов и заданий, возрастающие пороги, соответствие максимума последнему узлу, наличие основных ресурсов и сундука в наградах, согласованность метаданных ресурса и точный путь иконки `/img/weekly-rivalry/<resourceId>.png`.

Иконки находятся в `public/img/weekly-rivalry` и проходят через общий `AppImage` boundary. Все пути ассетов проверяются тестом. Отсутствующая иконка показывает контролируемое состояние общего image boundary и не меняет формулу.

## Failure And Guardrails

- отрицательные, дробные, бесконечные и слишком большие количества не попадают в расчёт как есть;
- один узел или задание нельзя применить повторно;
- будущую награду нельзя использовать заранее;
- при выключенном общем переключателе зоны нельзя смешивать;
- сундук всегда равен ровно одному основному ресурсу;
- галочки одного события и его ввод не должны попадать в другое событие;
- ошибка чтения storage не роняет экран и использует начальное состояние, а ошибка записи показывает контролируемое предупреждение без потери локального расчёта;
- `Антиквариат` и `Призыв` не импортируются для реализации этой функции;
- новый аналогичный экран подключается конфигурацией, а не копией модели, hook или больших компонентов;
- локальный snapshot не представляется как live-гарантия игры.

## Verification

Контракт проверяется на трёх конфигурациях:

- целостность данных и существование всех иконок;
- границы 16 узлов и 30 заданий каждого события;
- нормализация, numeric limits, schema version и независимые storage keys;
- все `16` сочетаний четырёх галочек для каждого события;
- изоляция зон без общей галочки и взаимный монотонный каскад с ней;
- участие собственных сундуков в обеих зонах и заработанных сундуков только согласно галочкам;
- завершённые состояния строк и наград разделов;
- динамическая шкала и конфигурационный `isSpecial`;
- карточки кешбэка с иконками и нулевыми значениями без служебного дублирования;
- общая архитектура трёх экранов, event-specific тексты, навигация и инструкция;
- четыре выключенные галочки по умолчанию и после сброса.
