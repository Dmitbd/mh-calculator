# Продуктовые контракты

## Где хранится решение

- Действующее продуктовое решение хранится в существующем `docs/*-spec.md` самостоятельной функции, которой оно принадлежит.
- Spec фиксирует текущий контракт: назначение, маршруты, состояния формы, ветвления сценария, данные, ошибки, ограничения и проверки. Он не является журналом обсуждений или планом реализации.
- Вкладка, поле, форма, режим, фильтр, инструкция и техническая route-обёртка обновляют родительский capability spec и не получают отдельный постоянный документ.
- Новый spec создаётся только для новой самостоятельной функции со своим назначением и пользовательской точкой входа.
- Общие инженерные решения о директориях, зависимостях и подходах хранятся в `docs/guidelines/`; перечень выпущенных функций и принадлежность маршрутов — в `docs/README.md`; ещё не реализованные согласованные задачи — в `docs/BACKLOG.md`.
- Временные планы, brainstorming и промежуточные аудиты не являются источником истины и не попадают в Git.

Такое размещение выбрано намеренно: форма или ветка сценария должна находиться рядом с остальными инвариантами той же функции, чтобы будущая правка не могла обнаружить только часть решения в отдельном документе.

## Каталог функций и маршрутов

Каждый раздел самостоятельной функции в `docs/README.md` содержит ровно:

- одну строку `Маршруты` с полным явным перечнем её route;
- одну строку `Контракт` со ссылкой на один capability spec.

Сокращения вроде «и одноимённые `/manual`» запрещены: автоматическая проверка должна сопоставить каждый файл в `app/` с одним владельцем. Несколько route одной функции, включая инструкцию и динамический detail-screen, остаются под одним spec.

Главная `/` является навигационной оболочкой и документируется отдельным разделом каталога с точной фразой `отдельный spec не требуется`. Это единственное текущее исключение. Один route нельзя назначать двум функциям, а каталог не может содержать отсутствующий route.

## Изменение поведения

В одном изменении необходимо:

1. Установить фактическое поведение по коду и тестам и сверить его с capability spec.
2. Зафиксировать новое или изменённое решение в родительском spec: не только happy path, но и состояние ошибки, сброс, отмену, конкурентные действия и запреты, если они важны для продукта.
3. Добавить или обновить behavior tests, которые защищают решение от случайного возврата старого поведения.
4. При изменении route или самостоятельной функции обновить `docs/README.md` и корневой `README.md`.
5. При пользовательском изменении обновить `docs/CHANGELOG.md#unreleased`.
6. При изменении owner, директории, public API или разрешённой зависимости синхронно обновить guideline, исполняемый architecture gate и его fixtures.
7. Выполнить `npm run docs:check` и остальные затронутые проверки.

Если код и spec расходятся, нельзя молча объявлять одну сторону правильной. Сначала определяется реально выпущенное и утверждённое поведение, затем код, тест и документ приводятся к одному контракту.

## Проверяемые гарантии

`npm run docs:check` использует тот же route inventory, что и route-тест, и завершается ошибкой, если:

- route отсутствует в каталоге, в owning spec, задокументирован дважды или больше не существует в `app/`;
- функция не имеет ровно одного существующего capability spec или один spec ошибочно разделён между несколькими capability-разделами;
- `docs/*-spec.md` потерялся из каталога;
- один из семи текущих самостоятельных capability specs удалён вместе со всеми изменяемыми ссылками; канонический набор защищён отдельным required inventory в checker;
- spec не достижим из `AGENTS.md` или корневого `README.md`, а `AGENTS.md` не ведёт к каталогу и этим правилам;
- guideline не достижим из `docs/guidelines/README.md`;
- постоянная Markdown-документация содержит несуществующую локальную inline/reference-style ссылку или ссылку на отсутствующий Markdown heading.

Временные `docs/superpowers/` и `.superpowers/` исключены из проверки содержимого только пока они остаются untracked. Checker отдельно читает Git index и завершает проверку ошибкой для файлов в этих каталогах, а также для Markdown-путей с маркерами `brainstorm`, `plan` или `plans` в имени файла либо сегменте каталога. Постоянные будущие задачи хранятся в `docs/BACKLOG.md`, поэтому временный документ нужно называть явно как план и не добавлять в Git.
