# Hero Localization and ID Migration Design

Date: 2026-07-19

## Goal

Bring every affected hero name in MH Calculator in line with the current Russian and English localization of Mythic Heroes, and migrate the misspelled canonical hero id `nephyths` to `nephthys` across local data, assets, application behavior, tests, exports, and Supabase.

The migration is intentionally strict. The application will not retain aliases, redirects, import normalization, or any other backward support for the old `nephyths` id.

## Source of Truth

The current Mythic Heroes localization data extracted from the Russian and English text bundles is the source of truth for the corrected display names. Local `heroes.json` remains the runtime source of truth after these corrections are committed.

## Canonical ID Migration

Only one corrected English name changes its kebab-case id:

- Old id: `nephyths`
- New id: `nephthys`

The new id becomes canonical everywhere:

- `heroes.json` hero id;
- hero icon path;
- icon filename under `public/img/heroes`;
- route parameter generated by `generateStaticParams`;
- build registry keys and build filenames if a Nephthys build is added or found;
- exported `heroId` values;
- Supabase `hero_build_sets.hero_id` values;
- nested `heroId` values in Supabase JSON payloads.

The case-only corrections `Sun WuKong` to `Sun Wukong` and `Yi Sun-Shin` to `Yi Sun-shin` do not change their existing canonical ids, `sun-wukong` and `yi-sun-shin`.

## Local Project Changes

`src/features/game-data/heroes/heroes.json` will receive all Russian and English display-name corrections. Its Nephthys record will also change from `nephyths` to `nephthys`, including the icon reference.

`public/img/heroes/nephyths.png` will be renamed to `public/img/heroes/nephthys.png`. No duplicate file or compatibility copy will remain.

All production code, committed JSON, tests, fixtures, accessibility labels, assertions, and documentation within the repository will be searched for the old values. Every domain occurrence will be updated to the corrected value. Unrelated prose that explicitly documents the migration may mention old values for historical clarity.

No runtime alias map will be introduced. `getHeroById("nephyths")`, the old route, and imported data containing the old id are allowed to fail under the existing unknown-hero behavior.

## Supabase Migration

A new timestamped SQL migration will update `public.hero_build_sets` without editing the original table-creation migration.

The migration will run as one explicit transaction and perform these operations:

1. Detect a primary-key collision where an old `nephyths` row and a new `nephthys` row share the same `status`.
2. Raise an exception before changing data if such a collision exists. The migration must not silently choose or overwrite one build.
3. Replace exact JSON string values in every `payload` for all corrected Russian and English hero names.
4. Replace exact nested JSON string values `nephyths` with `nephthys`.
5. Update `hero_build_sets.hero_id` from `nephyths` to `nephthys`.
6. Commit only if every operation succeeds.

Exact JSON values are replaced, not arbitrary substrings inside descriptive text. JSON objects, arrays, numbers, booleans, and null values remain unchanged.

The migration applies to both `draft` and `published` rows. RLS policies and the table schema do not change.

If the repository is linked to the intended remote Supabase project and authenticated CLI access is available, the verified migration will be applied remotely. If remote linkage or credentials are unavailable, implementation must stop short of pretending the remote database was changed and report the exact missing prerequisite.

## Data Flow After Migration

The frontend continues to load the local catalog and uses its stable kebab-case ids for routes and build lookups. Supabase continues to store the same build-set contract, but all affected payload labels use corrected game-localized names and all Nephthys relationships use `nephthys`.

There is no translation or compatibility layer between frontend and backend. Both sides must contain the corrected canonical values at deployment time.

## Failure Behavior

- A Supabase id collision aborts the entire SQL transaction.
- Any remaining old production value is treated as a failed integrity check.
- Old `/heroes/nephyths` URLs are not generated or redirected.
- Old exported JSON containing `nephyths` is not normalized during import.
- Missing or incorrectly renamed hero assets fail the existing asset-integrity checks or web export verification.

## Testing and Verification

Implementation follows test-first development.

The catalog integrity suite will gain an explicit expected mapping for every corrected hero and verify:

- all 14 Russian values;
- all 3 English values;
- the `nephthys` id and icon path;
- absence of `nephyths` from runtime catalog ids and icon references;
- continued uniqueness of all hero ids.

Existing tests and fixtures that assert corrected Russian labels will be updated only after a failing test demonstrates the old value.

Verification must include:

- focused catalog integrity tests;
- all Jest tests;
- TypeScript validation through the existing Expo/web build path;
- static web export, including generated hero routes;
- repository-wide search for obsolete production values;
- local Supabase migration verification when the required local runtime is available;
- remote migration status when remote application is authorized and available.

## Out of Scope

- Compatibility aliases or redirects for `nephyths`;
- automatic normalization of old user-exported JSON;
- changes to hero roles, factions, elements, rarity, release dates, or builds;
- mythological or linguistic corrections that differ from the current game localization;
- unrelated refactoring of the hero catalog, backend repository, or routing architecture.
