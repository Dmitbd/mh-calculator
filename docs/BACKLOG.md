# Бэклог MH Calculator

Этот документ хранит согласованные задачи, которые ещё не реализованы. Он не описывает текущее поведение приложения и не заменяет постоянные `docs/*-spec.md` или `CHANGELOG.md`.

При реализации задача переносится из backlog в соответствующий capability spec и `CHANGELOG.md` одновременно с кодом и тестами.

## Загрузка экранов и изображений

### BL-001 — Устранить задержку появления иконок

**Проблема.** Контент экрана появляется раньше иконок. Изображения догружаются и декодируются с заметной задержкой, из-за чего интерфейс выглядит незавершённым и может визуально пересобираться.

**Желаемый результат.** Критические изображения готовы к моменту показа основного содержимого, а остальные появляются через стабильный placeholder без изменения размеров элементов.

**Что исследовать и реализовать:**

- измерить отдельно сетевую загрузку, чтение из кеша и декодирование изображений на web и поддерживаемых native-платформах;
- определить критический набор изображений для первого экрана и загружать его до показа основного содержимого;
- использовать общий компонент изображения с memory/disk cache и единым состоянием placeholder/error;
- не блокировать весь экран ожиданием изображений ниже первого viewport;
- проверить влияние GitHub Pages `baseUrl` и `assetOrigin` на загрузку ассетов;
- сохранить фиксированные размеры контейнеров, чтобы позднее изображение не вызывало layout shift.

**Критерии готовности:**

- при холодной загрузке нет пустых мест или скачков размеров вместо критических иконок;
- при повторном открытии кешированные изображения появляются без заметной задержки;
- ошибка одного изображения показывает контролируемую заглушку и не блокирует экран;
- поведение покрыто тестами общего компонента и проверено на production web export.

## Online/offline данные

### BL-004 — Bootstrap-проверка backend и выбор источника данных

**Решение.** Вместо отдельного ping интернета использовать лёгкую backend-ручку `/bootstrap`. Её успешный ответ одновременно подтверждает сеть, доступность приложения backend и совместимость данных. `navigator.onLine` или аналогичный platform API может быть только подсказкой и не считается источником истины.

**Предлагаемый ответ:**

```json
{
  "status": "ok",
  "contentVersion": "2026-08-12.1",
  "schemaVersion": 1,
  "resources": {
    "heroBuilds": {
      "version": "2026-08-12.1",
      "etag": "sha256:..."
    }
  }
}
```

**Сценарий запуска:**

1. Приложение входит в состояние `checking` и показывает `ScreenLoader`.
2. `/bootstrap` вызывается с ограниченным настраиваемым timeout.
3. Совместимый успешный ответ переводит приложение в remote-сценарий.
4. Отсутствие сети, timeout, `5xx`, невалидный ответ или несовместимая `schemaVersion` переводят приложение в fallback-сценарий.
5. Ошибка отдельного resource-запроса переключает на fallback только соответствующую функцию, даже если `/bootstrap` ранее был успешен.
6. Уже показанные корректные данные не скрываются при последующей фоновой перепроверке.

**Почему не обычный health check.** Ответ `200` от health-ручки не гарантирует, что доступны база и нужные данные, а дополнительный ping увеличивает время старта и оставляет гонку между проверкой и настоящим запросом. Bootstrap должен проверять необходимые зависимости либо возвращать manifest, который можно сразу использовать для загрузки.

**Критерии готовности:**

- выбор `remote | fallback` реализован как единая тестируемая state machine;
- приложение не выполняет отдельный запрос к внешнему сайту только ради проверки интернета;
- все ветки bootstrap имеют ограниченное время ожидания и контролируемый результат;
- временный сбой одной функции не уничтожает last-known-good данные других функций;
- причины перехода на fallback доступны для диагностики, но не ломают пользовательский сценарий.

### BL-005 — Версионированные локальные snapshots из backend

**Цель.** Локальные JSON для offline/fallback не поддерживаются вручную и не расходятся незаметно с backend. Backend остаётся основным источником, а приложение получает проверенную резервную копию данных.

**Модель источников:**

1. `remote` — актуальные проверенные backend-данные;
2. `last-known-good` — последняя успешно загруженная и провалидированная версия в локальном кеше пользователя;
3. `bundled snapshot` — JSON, поставленный вместе с текущей версией приложения.

Fallback выбирает наиболее новый совместимый `last-known-good`; если его нет или он повреждён, используется bundled snapshot.

**Обновление bundled snapshot:**

- добавить отдельный export-скрипт, который получает опубликованные данные backend и записывает детерминированные файлы в `src/features/game-data/snapshots/`;
- хранить рядом manifest с `contentVersion`, `schemaVersion`, стабильной датой версии backend-контента и checksum каждого файла;
- до записи проверять runtime-схему, уникальность ID, ссылки между каталогами и существование обязательных ассетов;
- одинаковые backend-данные должны создавать byte-identical content-файлы и manifest без случайного порядка и локального времени запуска экспорта;
- GitHub Action запускает экспорт вручную и/или по расписанию, а изменение snapshot проходит через отдельный PR, тесты и review; workflow не пишет напрямую в `main`;
- секрет с правом чтения backend используется только в CI и не попадает в generated JSON, логи или клиентский bundle;
- невалидный экспорт завершает workflow ошибкой и сохраняет предыдущий snapshot.

**Runtime cache:**

- кеш обновляется только после полной загрузки и успешной проверки resource;
- payload и manifest записываются как одна логическая версия, чтобы приложение не смешивало данные разных выпусков;
- несовместимый `schemaVersion`, неверный checksum или прерванная запись не заменяют last-known-good;
- очистка кеша не должна удалять bundled snapshot.

**Критерии готовности:**

- свежая установка без сети открывает bundled данные;
- пользователь после успешной online-загрузки получает те же или более новые данные offline без нового релиза приложения;
- генерация snapshot воспроизводима локально и в CI;
- обновление backend-контента не требует ручного копирования отдельных JSON;
- тесты покрывают приоритет источников, несовместимую схему, повреждённый кеш и неудачный экспорт.

## Рекомендуемый порядок

2. `BL-005` — versioned snapshot, runtime cache и CI-обновление.
3. `BL-001` — preload/cache изображений на основе измерений уже стабилизированной загрузки экранов.
